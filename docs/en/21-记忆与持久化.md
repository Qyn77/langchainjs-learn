## 🤔 Why Do You Need Persistence?

Look back at Chapter 09: in LangChain v1.x we **kept the message array by hand** to implement memory. LangGraph offers a more systematic approach — the **Checkpointer**:

```
Each time the graph runs, LangGraph saves a State snapshot (checkpoint) at every superstep boundary
                │
                ▼
Snapshots are grouped by thread (conversation), and thread_id tells conversations apart
                │
                ▼
The next call with the same thread_id → loads the previous State and continues
```

Persistence gives you four capabilities:

| Capability | What it means |
|------|------|
| **Conversation memory** | Several calls on the same thread share State (multi-turn conversation) |
| **Human-in-the-loop** | The graph can pause, wait for a person, then resume (Chapter 22) |
| **Fault-tolerant recovery** | After a node fails, rerun from the latest checkpoint |
| **Time travel** | Look back at, or replay, past runs (a powerful debugging tool) |

---

## 📦 MemorySaver: An In-Memory Checkpointer

`MemorySaver` stores checkpoints in memory. It is the best fit for learning and tests:

```javascript
import { MemorySaver } from "@langchain/langgraph";

const checkpointer = new MemorySaver();

// Attach the checkpointer at compile time
const graph = builder.compile({ checkpointer });
```

> ⚠️ **Important:** Once a checkpointer is attached, **every call to the graph must provide a `thread_id`**. Otherwise State cannot be saved or restored.

## 💡 Full Example: Multi-Turn Conversation Memory

Create `memory-demo.js` (a ReAct Agent version):

```javascript
import { ChatOpenAI } from "@langchain/openai";
import { HumanMessage } from "@langchain/core/messages";
import { tool } from "@langchain/core/tools";
import { createReactAgent } from "@langchain/langgraph/prebuilt";
import { MemorySaver } from "@langchain/langgraph";
import { z } from "zod";

const model = new ChatOpenAI({
  model: "MiniMax/MiniMax-M2.5",
  apiKey: process.env.MODELSCOPE_API_KEY,
  configuration: {
    baseURL: "https://api-inference.modelscope.cn/v1",
  },
});

const timeTool = tool(
  async () => new Date().toLocaleString("en-US"),
  {
    name: "get_time",
    description: "Get the current date and time",
    schema: z.object({}),
  }
);

// 1. Create the Checkpointer
const checkpointer = new MemorySaver();

// 2. Attach it when you create the Agent
const agent = createReactAgent({
  llm: model,
  tools: [timeTool],
  prompt: "You are a friendly AI assistant. Remember what the user tells you.",
  checkpointSaver: checkpointer,   // ← the key argument
});

// 3. Use the same thread_id on every call
const config = { configurable: { thread_id: "conversation-1" } };

// Turn 1
let result = await agent.invoke(
  { messages: [new HumanMessage("My name is Alex, and I am 25")] },
  config
);
console.log("AI:", result.messages[result.messages.length - 1].content);

// Turn 2: a brand-new call, but the same thread
result = await agent.invoke(
  { messages: [new HumanMessage("What is my name? How old am I?")] },
  config   // ← the same thread_id
);
console.log("AI:", result.messages[result.messages.length - 1].content);
```

What a run looks like:

```
AI: Hi Alex! Nice to meet you. I'll remember that.
AI: Your name is Alex, and you are 25.
    ↑ The second call did not resend the first turn's messages, but the AI remembers!
```

### Where does the memory live?

It lives in the **thread's State**. On the second `invoke`, LangGraph automatically loads the full `messages` history saved on the `conversation-1` thread, and the new message is appended after it. You no longer push onto a message array by hand the way Chapter 09 did.

> 💡 **A different thread_id is a new conversation.** Change `thread_id` to `"conversation-2"` and ask "what is my name?" again, and the AI will not remember. In a support system, giving each user session its own thread_id is that simple.

## 🔍 getState: Inspect Graph State

```javascript
const state = await agent.getState(config);

console.log(state.values);       // the full State right now { messages: [...] }
console.log(state.next);         // the nodes that will run next (an empty array means the run is finished)
console.log(state.metadata.step); // which superstep the run has reached
```

### Common StateSnapshot fields

| Field | Description |
|------|------|
| `values` | The full State at that checkpoint |
| `next` | Array of node names to run next (`[]` means the run is finished) |
| `metadata` | Metadata: `step` (the step count), `writes` (which node wrote what), `source` |
| `createdAt` | When the checkpoint was created |
| `tasks` | The task list for the current step (includes interrupt info, used in Chapter 22) |

## 🕰️ getStateHistory: Time Travel

**Every step** of a graph run has a checkpoint, so you can look back over the whole run:

```javascript
const config = { configurable: { thread_id: "conversation-1" } };

// Walk every checkpoint from newest to oldest
for await (const snapshot of agent.getStateHistory(config)) {
  console.log(
    `step=${snapshot.metadata.step}`,
    `next=${snapshot.next}`,
    `messageCount=${snapshot.values.messages?.length}`
  );
}
```

Sample output:

```
step=3 next=[] messageCount=4          ← the last run finished
step=2 next=[] messageCount=3
step=1 next=[] messageCount=2
step=0 next=['agent'] messageCount=1   ← the input just arrived
```

This is extremely useful when debugging an Agent. "What did it actually receive on step 3?" Open the checkpoint and you can see.

### Editing State by hand: updateState

```javascript
// Manually update State as if a node wrote it (the field's reducer still runs)
await agent.updateState(config, {
  messages: [new HumanMessage("(Added by a human: my favorite color is blue)")],
});
```

> 💡 **Note:** `updateState` creates a **new checkpoint**. It does not change history. Together with human-in-the-loop (Chapter 22), you can build a flow where a person reviews and edits the Agent's State.

## 💾 Production: Persist to a Database

`MemorySaver` lives in memory, so **a process restart wipes it**. In production, switch to a Checkpointer backed by a database. The interface stays the same:

| Package | Storage | Install |
|----|------|------|
| `@langchain/langgraph-checkpoint-sqlite` | SQLite | `npm i @langchain/langgraph-checkpoint-sqlite` |
| `@langchain/langgraph-checkpoint-postgres` | PostgreSQL | `npm i @langchain/langgraph-checkpoint-postgres` |

```javascript
// SQLite example (illustrative; follow that package's docs for the exact API)
import { SqliteSaver } from "@langchain/langgraph-checkpoint-sqlite";

const checkpointer = SqliteSaver.fromConnString("./memory.db");
const graph = builder.compile({ checkpointer });
```

> 💡 **Note:** Switching Checkpointers is a one-line change. Business code stays the same. That is the benefit of the shared interface.

## ✂️ Managing Message History: Avoiding a Token Blowup

The longer a conversation goes, the more tokens it costs, and it can overflow the model's context window. Two common responses:

### Approach 1: Trim before you send to the model (the simplest)

Keep the full history in State, but **send the model only the latest N messages**:

```javascript
async function callModel(state) {
  // Send only the latest 10 messages to the model; the full history stays in State
  const recentMessages = state.messages.slice(-10);
  const response = await model.invoke(recentMessages);
  return { messages: [response] };
}
```

> 💡 **Note:** Trimming only affects what is sent to the model. `state.messages` itself does not change. This is the most common way to control tokens in a multi-turn Agent.

### Approach 2: Wipe and start over (REMOVE_ALL_MESSAGES)

The library provides a special marker, `REMOVE_ALL_MESSAGES`. Return it together with the messages that follow, and the history is **cleared first, then the new messages are appended**:

```javascript
import { REMOVE_ALL_MESSAGES } from "@langchain/langgraph";

// Clear the conversation history and start again from this new message
return { messages: [REMOVE_ALL_MESSAGES, new HumanMessage("Let's talk about something new")] };
```

> 💡 **Further reading:** More message operations (delete a message by id, trim tool messages in the middle, and so on) are in the official docs: [add-memory](https://docs.langchain.com/oss/javascript/langgraph/add-memory).

## ⚠️ Things to Watch Out For

### 1. A checkpointer means you must pass thread_id

```javascript
// ❌ Error: a checkpointer requires thread_id
await graph.invoke(input);

// ✅ Right
await graph.invoke(input, { configurable: { thread_id: "1" } });
```

### 2. MemorySaver forgets everything on restart

In-memory storage is only for local development and debugging. To keep State across processes or machines, use the SQLite or Postgres Checkpointer.

### 3. updateState on a reducer field appends

The `messages` field's reducer appends. Messages written with `updateState` are **appended** to the end of the history. They do not overwrite it.

### 4. State must be serializable

Checkpoints are written to storage, so State fields must be JSON-serializable (the rule from Chapter 17).

## 📝 Chapter Summary

- A Checkpointer saves a State snapshot at every superstep, organized by `thread_id`
- The in-memory `MemorySaver`: `compile({ checkpointer })`, and pass `{ configurable: { thread_id } }` on each call
- Several calls with the same thread_id automatically share State → **multi-turn conversation memory**
- `getState` shows the current State, `getStateHistory` replays the run, and `updateState` edits State by hand
- In production, switch to a SQLite or Postgres Checkpointer. The interface stays the same
