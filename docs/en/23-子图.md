# 23-Subgraphs: A Graph Inside a Graph

> 📅 For LangGraph.js v1.x | 👶 Beginner-friendly
> 💡 **Note:** Requires Node.js 18+

---

## 🎯 Goals for This Chapter

- ✅ Understand what subgraphs are for: reuse, divide-and-conquer, and the foundation of multi-agent systems
- ✅ Master the two integration styles: use one directly as a node, or call it inside a node
- ✅ Learn the persistence (checkpointer) rules for subgraphs

---

## 🤔 What Is a Subgraph?

**A subgraph is another graph used as a "node."**

```
Parent graph:
START → [Node A] → [subgraph as a whole] → [Node B] → END
                       │
                       ▼
                  Inside the subgraph:
                  sub1 → sub2 → sub3
```

Why do you need one?

| Need | What a subgraph does |
|------|----------------------|
| **Reuse** | One "search + summarize" flow is used in several graphs → package it as a subgraph |
| **Divide and conquer** | A big graph gets messy → split it by business area into smaller graphs, each written on its own |
| **Teamwork** | Different teams maintain different subgraphs, as long as they agree on inputs and outputs |
| **Multi-agent** | Each agent is a subgraph (the star of Chapter 24) |

---

## 🔀 Two Integration Styles (Which One?)

| Style | When to use it | How to write it |
|------|----------------|-----------------|
| **Style 1: Use it directly as a node** | The parent graph and the subgraph **share state fields** (for example both use `MessagesAnnotation`) | `addNode("name", compiled subgraph)` |
| **Style 2: Call it inside a node** | The parent graph and the subgraph **have different state**, so you convert it by hand | `subgraph.invoke(...)` inside the node function |

---

## 💡 Style 1: Shared State, Use It Directly as a Node

The subgraph and the parent graph use the same state definition. Once the subgraph is compiled, you can pass it straight to `addNode`.

Create `shared-state-subgraph.js`:

```javascript
import { Annotation, StateGraph, START, END } from "@langchain/langgraph";

// ===== Shared state definition (both the parent and the subgraph use it) =====
const StateAnnotation = Annotation.Root({
  text: Annotation,
  summary: Annotation,
});

// ===== Define the subgraph: search + distill =====
const subgraph = new StateGraph(StateAnnotation)
  .addNode("analyze", (state) => {
    console.log("  [subgraph] Analyzing text:", state.text);
    return { summary: `The core idea of "${state.text}" is...` };
  })
  .addEdge(START, "analyze")
  .addEdge("analyze", END)
  .compile();

// ===== Parent graph: preprocess → subgraph → output =====
const graph = new StateGraph(StateAnnotation)
  .addNode("clean", (state) => {
    console.log("[parent] Preprocessing text");
    return { text: state.text.trim() };
  })
  // ★ The compiled subgraph is used directly as a node!
  .addNode("analyzeFlow", subgraph)
  .addNode("report", (state) => {
    console.log("[parent] Generating the report based on:", state.summary);
    return {};
  })
  .addEdge(START, "clean")
  .addEdge("clean", "analyzeFlow")
  .addEdge("analyzeFlow", "report")
  .addEdge("report", END)
  .compile();

await graph.invoke({ text: "  LangGraph makes agent orchestration simple  " });
```

Sample output:

```
[parent] Preprocessing text
  [subgraph] Analyzing text: LangGraph makes agent orchestration simple
[parent] Generating the report based on: The core idea of "LangGraph makes agent orchestration simple" is...
```

> 💡 **Note:** The indentation of `console.log` inside the subgraph shows the execution order: parent node → nodes inside the subgraph → parent node. It is scheduled into the execution flow exactly like an ordinary node.

A subgraph can also have its own **private fields**. The subgraph's state definition can include a few extra fields the parent does not have. The parent never sees those extra fields and is not affected by them (those keys simply do not exist on the parent state; the subgraph uses them only internally).

## 💡 Style 2: Different State, Call It Inside a Node

When the parent graph and the subgraph have completely different state fields, write a "translation node" that converts the state:

Create `different-state-subgraph.js`:

```javascript
import { Annotation, StateGraph, START, END } from "@langchain/langgraph";

// ===== Subgraph state: completely different from the parent =====
const SubgraphState = Annotation.Root({
  keyword: Annotation,   // the subgraph only cares about keyword
  hits: Annotation({     // the subgraph's own search results
    reducer: (a, b) => a.concat(b),
    default: () => [],
  }),
});

const subgraph = new StateGraph(SubgraphState)
  .addNode("search", (state) => {
    console.log("  [subgraph] Searching:", state.keyword);
    return { hits: [`${state.keyword}-result-1`, `${state.keyword}-result-2`] };
  })
  .addEdge(START, "search")
  .addEdge("search", END)
  .compile();

// ===== Parent graph state =====
const StateAnnotation = Annotation.Root({
  query: Annotation,     // the parent calls it query; the subgraph calls it keyword — the names do not even match
  docs: Annotation({     // the parent calls it docs; the subgraph calls it hits
    reducer: (a, b) => a.concat(b),
    default: () => [],
  }),
});

const graph = new StateGraph(StateAnnotation)
  .addNode("doSearch", async (state) => {
    // 1️⃣ Parent state → subgraph state (convert the input)
    const subResult = await subgraph.invoke({ keyword: state.query });
    // 2️⃣ Subgraph result → parent state (convert the output)
    return { docs: subResult.hits };
  })
  .addEdge(START, "doSearch")
  .addEdge("doSearch", END)
  .compile();

const result = await graph.invoke({ query: "LangGraph tutorial" });
console.log(result.docs);
// [ 'LangGraph tutorial-result-1', 'LangGraph tutorial-result-2' ]
```

> 💡 **When should you use style 2?** The most typical case is a multi-agent system where each agent has its own **private message history** and only the final reply is synced back to the main conversation. Names do not match and fields do not line up, so the node function converts everything by hand.

## 💾 Persistence Rules for Subgraphs

A subgraph's checkpointer has three modes (set **when you compile the subgraph**):

| Mode | How you compile it | Behavior |
|------|--------------------|----------|
| **Default (recommended)** | `.compile()` | No checkpointer of its own. Each call starts from scratch, but it **inherits the parent graph's checkpointer** (an `interrupt` inside the subgraph can still pause and resume normally) |
| **Independent memory** | `.compile({ checkpointer: new MemorySaver() })` | Subgraph state is kept across calls — a good fit when a sub-agent needs multi-turn memory |
| **Fully stateless** | `.compile({ checkpointer: false })` | Runs like an ordinary function and does not support `interrupt` |

> ⚠️ **Prerequisite:** The parent graph itself must have a checkpointer attached. Only then do the subgraph's persistence and `interrupt` take effect.

```javascript
// Example: independent memory for the subgraph (keeps its own state across multiple parent calls)
const subgraph = subgraphBuilder.compile({ checkpointer: new MemorySaver() });

// The parent is invoked twice; on the second call the subgraph can "remember" the first
const parent = new StateGraph(StateAnnotation)
  .addNode("mySub", subgraph)
  ...
  .compile({ checkpointer: new MemorySaver() });
```

## 🔍 Inspecting What Happens Inside a Subgraph

When streaming, add `subgraphs: true` and you can see every update inside the subgraph (Chapter 25 covers streaming in detail):

```javascript
const stream = await graph.stream(
  { query: "LangGraph tutorial" },
  { subgraphs: true, streamMode: "updates" }
);

for await (const [namespace, update] of stream) {
  // An empty namespace [] means the parent graph; a non-empty one means inside the subgraph
  console.log(`[${namespace.join("/") || "parent"}]`, JSON.stringify(update));
}
```

Sample output:

```
[parent] {"doSearch":{...}}            ← parent node
[doSearch:uuid] {"search":{...}}     ← a node inside the subgraph
[doSearch:uuid] {"__end__":null}
[parent] {"__end__":{...}}
```

## ⚠️ Things to Watch Out For

### 1. Style 1 requires the subgraph to be compiled first

```javascript
// ❌ Wrong: addNode was given an uncompiled builder
.addNode("sub", subgraphBuilder)

// ✅ Correct: call .compile() first, then pass it in
.addNode("sub", subgraphBuilder.compile())
```

### 2. Shared fields really must be "the same name and the same meaning"

Style 1 depends on state field names matching exactly. If the parent calls a field `docs` and the subgraph calls it `hits`, they are not shared — either use the same names, or use style 2 and convert by hand.

### 3. Do not form a cycle between the subgraph and the parent

A subgraph can contain cycles internally, but the call chain parent → subgraph → parent must avoid an infinite loop (like an ordinary cycle, it is protected by `recursionLimit`).

### 4. Remember to check the checkpointer when you use interrupt

Using `interrupt` inside a subgraph requires the parent to have a checkpointer attached (the default mode inherits it automatically).

---

## 📝 Chapter Summary

- A subgraph is a graph used as a node, for **reuse, divide-and-conquer, and multi-agent systems**
- Shared state → after compiling, call `addNode("name", compiledSubgraph)` directly
- Different state → call `subgraph.invoke()` inside the node function and convert inputs and outputs by hand
- By default a subgraph inherits the parent checkpointer; it can also keep independent memory, or be fully stateless
- `stream({ subgraphs: true })` lets you see every step inside the subgraph
