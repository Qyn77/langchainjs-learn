## 📦 Nodes in Depth

### The standard shape of a node

A node is a function:

```javascript
// Synchronous node
const nodeA = (state) => {
  return { foo: state.foo + 1 };  // return a State update
};

// Asynchronous node (calling an LLM or an API is asynchronous)
const nodeB = async (state) => {
  const response = await model.invoke(state.messages);
  return { messages: [response] };
};

// Register them on the graph
const graph = new StateGraph(StateAnnotation)
  .addNode("nodeA", nodeA)
  .addNode("nodeB", nodeB)
  ...
```

### The node's second argument: config

A node can also take a second argument, `config`, which carries runtime information:

```javascript
const myNode = async (state, config) => {
  // config.configurable: options passed in when the graph is invoked
  const userId = config.configurable?.userId;

  // config.writer: send custom data to the stream (covered in Chapter 25)
  config.writer?.({ progress: "Working..." });

  return { /* update */ };
};
```

### Returning Command: update State and choose the next node in one step

By default, a node only returns a State update. Edges decide where to go next. A node can also return a `Command` and specify both at once:

```javascript
import { Command } from "@langchain/langgraph";

const routerNode = (state) => {
  if (state.score >= 60) {
    // Update State and jump to a named node
    return new Command({
      update: { result: "pass" },
      goto: "celebrate",           // next stop: the celebrate node (or END)
    });
  }
  return new Command({
    update: { result: "fail" },
    goto: "remedial",
  });
};
```

> 💡 **Note:** `Command`'s `goto` overlaps with conditional edges (Chapter 19). Rule of thumb: **use `Command` when the branch is simple (you skip writing a separate router). Use conditional edges when the branch is complex, or when you want to reuse the routing logic**.

## 🔗 Edges in Depth

### Plain edges: a fixed route

```javascript
.addEdge("nodeA", "nodeB")   // after A finishes, B always runs next
.addEdge(START, "nodeA")     // the graph's entry
.addEdge("nodeB", END)       // the graph's exit
```

### Fan-out: one node, then several nodes in parallel

**When several edges leave the same source node, the target nodes run in parallel** (in the same superstep):

```javascript
.addEdge("start_node", "nodeA")
.addEdge("start_node", "nodeB")  // nodeA and nodeB run in parallel
```

### Fan-in: several paths join

When several nodes all point at the same target, the target **waits until every upstream node has finished** before it runs:

```javascript
.addEdge("nodeA", "join")
.addEdge("nodeB", "join")  // join waits until both nodeA and nodeB have finished
```

> ⚠️ **Note:** If parallel nodes write the same State field, that field must have a reducer (the rule from Chapter 17).

## 💡 Walkthrough 1: A Three-Step Writing Pipeline

A sequential workflow: generate an outline → write the draft → polish it.

Create `writing-pipeline.js`:

```javascript
import { ChatOpenAI } from "@langchain/openai";
import { Annotation, StateGraph, START, END } from "@langchain/langgraph";

const model = new ChatOpenAI({
  model: "MiniMax/MiniMax-M2.5",
  apiKey: process.env.MODELSCOPE_API_KEY,
  configuration: {
    baseURL: "https://api-inference.modelscope.cn/v1",
  },
});

// Define State: each step's output uses overwrite semantics
const StateAnnotation = Annotation.Root({
  topic: Annotation,      // topic
  outline: Annotation,    // outline
  draft: Annotation,      // draft
  final: Annotation,      // final copy
});

// Node 1: generate an outline
async function generateOutline(state) {
  const res = await model.invoke(`Write a 3-point outline for the article "${state.topic}". Return only the outline.`);
  return { outline: res.content };
}

// Node 2: write the draft
async function writeDraft(state) {
  const res = await model.invoke(`Write a 150-word draft from the outline below:\n${state.outline}`);
  return { draft: res.content };
}

// Node 3: polish
async function polish(state) {
  const res = await model.invoke(`Polish the text below so it is more engaging:\n${state.draft}`);
  return { final: res.content };
}

// Build the graph: a straight pipeline
const graph = new StateGraph(StateAnnotation)
  .addNode("generateOutline", generateOutline)
  .addNode("writeDraft", writeDraft)
  .addNode("polish", polish)
  .addEdge(START, "generateOutline")
  .addEdge("generateOutline", "writeDraft")
  .addEdge("writeDraft", "polish")
  .addEdge("polish", END)
  .compile();

const result = await graph.invoke({ topic: "Everyday uses of AI" });

console.log("Outline:", result.outline);
console.log("Draft:", result.draft);
console.log("Final:", result.final);
```

Data flow:

```
START → generateOutline → writeDraft → polish → END
          (writes outline)  (reads outline   (reads draft
                             writes draft)    writes final)
```

## 💡 Walkthrough 2: A Fan-out / Fan-in Parallel Workflow

Two LLM calls run in parallel (one writes a joke, one writes a poem). Their results join, then a summary node reviews them.

Create `fan-out-in.js`:

```javascript
import { ChatOpenAI } from "@langchain/openai";
import { Annotation, StateGraph, START, END } from "@langchain/langgraph";

const model = new ChatOpenAI({
  model: "MiniMax/MiniMax-M2.5",
  apiKey: process.env.MODELSCOPE_API_KEY,
  configuration: {
    baseURL: "https://api-inference.modelscope.cn/v1",
  },
});

const StateAnnotation = Annotation.Root({
  topic: Annotation,
  // Parallel nodes all write this field → it must have a reducer!
  outputs: Annotation({
    reducer: (existing, update) => existing.concat(update),
    default: () => [],
  }),
  summary: Annotation,
});

// Parallel node 1: write a joke
async function writeJoke(state) {
  const res = await model.invoke(`Write a 50-word joke on the topic "${state.topic}".`);
  return { outputs: [`[Joke] ${res.content}`] };
}

// Parallel node 2: write a poem
async function writePoem(state) {
  const res = await model.invoke(`Write a 50-word short poem on the topic "${state.topic}".`);
  return { outputs: [`[Poem] ${res.content}`] };
}

// Join node: runs only after both branches have finished
async function summarize(state) {
  const res = await model.invoke(
    `Here are two pieces. Comment on each in one sentence:\n\n${state.outputs.join("\n\n")}`
  );
  return { summary: res.content };
}

const graph = new StateGraph(StateAnnotation)
  .addNode("writeJoke", writeJoke)
  .addNode("writePoem", writePoem)
  .addNode("summarize", summarize)
  // Fan-out: two edges leave START → writeJoke and writePoem run in parallel
  .addEdge(START, "writeJoke")
  .addEdge(START, "writePoem")
  // Fan-in: both point at summarize
  .addEdge("writeJoke", "summarize")
  .addEdge("writePoem", "summarize")
  .addEdge("summarize", END)
  .compile();

const result = await graph.invoke({ topic: "office life" });

console.log("Parallel outputs:", result.outputs);
console.log("Review:", result.summary);
```

Execution shape:

```
            ┌─→ [writeJoke] ─┐
START ──────┤  (in parallel) ├─→ [summarize] → END
            └─→ [writePoem] ─┘
```

> 💡 **Note:** `invoke()` waits until the whole graph finishes, then returns. To watch each step as it happens, use `stream()` (covered in Chapter 25).

## 🧩 Going Further: Private State and Input/Output Filtering (Optional Reading)

In a large graph, some intermediate fields should stay hidden from the outside (for example, a draft cache used only by internal nodes). LangGraph lets you declare three schemas for a graph: **overall State, an input schema, and an output schema**. Callers only see the fields declared in the input and output schemas:

```javascript
const graph = new StateGraph({
  state: OverallStateAnnotation,   // the full internal State (visible to every node)
  input: InputStateAnnotation,     // fields that invoke() must be given
  output: OutputStateAnnotation,   // the subset of fields invoke() returns when it finishes
});
```

While you are learning, one State definition is enough. Come back to this when the graph grows and you want a narrower input and output.

## ⚠️ Things to Watch Out For

### 1. Node names must be unique

```javascript
// ❌ Wrong: registering the same name twice throws
.addNode("agent", nodeA)
.addNode("agent", nodeB)
```

### 2. Connect every path to END

```
START → A → B → END    ✅
START → A → B (no edge to END) ⚠️ the graph may never reach a finish
```

### 3. A cycle must have an exit condition

Graphs are powerful because they can loop (for example, "call a tool → think again → call again"). Every loop needs a stop condition (usually a conditional edge, Chapter 19). Without one, you hit the recursion limit and get an error.

### 4. Parallel nodes writing the same field means a reducer is required

See Chapter 17. This is the most common source of errors.

## 📝 Chapter Summary

- A node is a function `(state, config) => update`, and it can be `async`
- `Command({ update, goto })` can update State and choose the next node from inside the node
- Several edges leaving one source = **parallel fan-out**. Several edges arriving at one node = **fan-in that waits**
- A sequential pipeline: each node can read and write different fields
- A parallel workflow: a shared field must have a reducer
